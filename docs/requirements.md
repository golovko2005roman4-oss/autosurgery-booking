# Техническое задание: AutoSurgery Booking — демонстрационный MVP онлайн-записи
## СТО «АвтоХирургия», Новосибирск

> Основание: `docs/research.md`.
> Это ТЗ на **демонстрационную** версию для показа владельцу СТО.
> Это **не** production-система и **не** CRM. Кодирование на этом этапе не начинается.

---

# 1. Цель проекта

Создать демонстрационный MVP системы онлайн-записи клиентов автосервиса, чтобы:

1. Показать владельцу СТО «АвтоХирургия», как может работать современная онлайн-запись: клиент сам выбирает услугу, дату и свободное время; администратор подтверждает заявки в панели.
2. Проверить на демо-данных полный цикл: заявка клиента → уведомление администратору → подтверждение/отклонение/перенос → выполнение.
3. Заложить архитектуру и структуру данных, пригодные для расширения до реальной системы после согласования с владельцем.

**Явно не является целью:** production-запуск для реальных клиентов (до уточнения раздела 16), CRM, оплата, интеграции.

# 3. User Stories

**Клиент:**
- US-1: Как клиент, я хочу выбрать услугу из списка, чтобы записаться на конкретную работу.
- US-2: Как клиент, я хочу указать марку и модель авто, чтобы механик знал, к чему готовиться.
- US-3: Как клиент, я хочу выбрать дату и видеть только свободное время, чтобы не звонить и не угадывать.
- US-4: Как клиент, я хочу оставить имя и телефон, чтобы администратор мог связаться со мной.
- US-5: Как клиент, я хочу получить подтверждение, что заявка принята, чтобы быть уверенным, что она не потерялась.

**Администратор:**
- US-6: Как администратор, я хочу видеть все новые заявки, чтобы не пропустить обращение.
- US-7: Как администратор, я хочу подтвердить или отклонить заявку, чтобы управлять расписанием.
- US-8: Как администратор, я хочу перенести заявку на другое время, чтобы разрулить коллизии.
- US-9: Как администратор, я хочу, чтобы занятый слот нельзя было забронировать дважды, чтобы не было двойных записей.

# 7. Состояния заявки

**Статусы:**

| Статус | Значение | Слот считается занятым? |
|---|---|---|
| `new` | Заявка создана клиентом, ждёт решения администратора | Нет (мягкое удержание не используем — демо) |
| `confirmed` | Администратор подтвердил, слот забронирован | **Да** |
| `cancelled` | Отклонена администратором (с причиной) | Нет |
| `completed` | Визит состоялся, заявка закрыта | Нет (история) |

**Допустимые переходы:**

```
new        → confirmed   (Подтвердить)
new        → cancelled   (Отклонить, обязательна причина)
confirmed  → completed   (Выполнено)
confirmed  → cancelled   (Отклонить, обязательна причина)
confirmed  → confirmed   (Перенести: атомарная смена слота)
```

**Запрещённые переходы** (кнопки не отображаются, сервер отклоняет): из `cancelled` и `completed` — любые; `new → completed` без подтверждения; повторное подтверждение уже подтверждённой заявки.

**Инвариант занятости:** на один слот не может существовать более одной заявки со статусом `confirmed`. Подтверждение/перенос выполняются атомарно (см. 8.5).

| brand | text | NOT NULL |

### 8.4. `bookings` — заявки

| Поле | Тип | Ограничения |
|---|---|---|
| id | uuid | PK |

| vehicle_id | uuid | FK → vehicles.id |
| service_id | uuid | FK → services.id |
| booking_date | date | NOT NULL — дата визита |
| booking_time | time | NOT NULL — время слота |
| status | text | NOT NULL, default 'new'; CHECK in ('new','confirmed','cancelled','completed') |

| created_at | timestamptz | NOT NULL, default now() |
| updated_at | timestamptz | NOT NULL, default now() |

Индексы: `(booking_date, booking_time)`, `(status)`.

### 8.5. Защита от двойного бронирования

Реализация — **частичный уникальный индекс** (простая и надёжная, без доп. таблиц слотов):

```sql
CREATE UNIQUE INDEX bookings_one_confirmed_per_slot
ON bookings (booking_date, booking_time)
WHERE status = 'confirmed';
```

- Подтверждение и перенос выполняются через RPC-функцию (`confirm_booking`, `reschedule_booking`), которая делает `UPDATE ... WHERE id = ... AND status = 'new'` (или `'confirmed'` для переноса) и перехватывает нарушение уникального индекса.
- При конфликте клиенту/администратору возвращается понятная ошибка: «Это время только что заняли, выберите другое».
- В `settings.capacity_per_slot` (см. 8.6) задел под будущую вместимость > 1: при росте capacity индекс заменяется на расширенную схему со слотами; до этого момента capacity = 1.

### 8.6. `settings` (при необходимости)

| Поле | Тип | Назначение |
|---|---|---|
| key | text | PK, напр. 'demo_schedule' |
| value | jsonb | напр. `{"demo_days": 14, "slots": ["09:00",...,"18:00"], "capacity_per_slot": 1}` |

Хранит демо-расписание, чтобы клиентская и админская части читали его из одного места.

# 9. Архитектура

### 9.1. Рекомендуемый стек

| Слой | Технология | Обоснование |
|---|---|---|
| Frontend + Backend | **Next.js (App Router)** | Один фреймворк для формы и админки; server actions/API routes без отдельного бэкенда; деплой на Vercel — бесплатно и мгновенно; лёгкое расширение до полноценного приложения |
| UI | **Tailwind CSS + shadcn/ui** | Быстрая сборка аккуратного mobile-first интерфейса из готовых доступных компонентов; минимум кастомного CSS |
| БД + Auth | **Supabase** (PostgreSQL, Auth, RLS) | Бесплатный тариф; готовая авторизация администратора; PostgreSQL с транзакциями и частичными индексами решает двойное бронирование на уровне данных; без собственного сервера |
| Уведомления | Telegram Bot API (опциональный модуль) | Владелец уже использует Telegram; простой fetch в server action при создании заявки; отсутствие настройки не ломает приложение |

**Почему не React+Vite с отдельным бэкендом:** для демо из 2 страниц и 5 таблиц отдельный API-сервер — избыточен: больше кода, деплой и поддержка. Next.js + Supabase покрывает всё с меньшим объёмом инфраструктуры, и при этом является production-стеком — демо можно развивать, а не переписывать.

**Почему не Firebase:** слабее реляционная модель; правило «один подтверждённый на слот» пришлось бы гарантировать кодом, а не индексом.

### 9.2. Диаграмма потоков

```
Клиент (мобильный браузер)
   │  форма записи (шаги 1–5)
   ▼
Next.js (server action: create_booking)
   │  INSERT clients/vehicles/bookings(status='new')
   │  (опц.) POST Telegram Bot API
   ▼
Supabase (PostgreSQL, RLS)
   │
   ▼
Администратор — /admin (Supabase Auth)
   │  подтвердить/отклонить/перенести/выполнить
   ▼
RPC confirm_booking / reschedule_booking (транзакция + уникальный индекс)
```

# 10. Безопасность

1. **Валидация телефона:** маска `+7 (9XX) XXX-XX-XX`; на сервере — нормализация до цифр и проверка длины 11, начала с `7`/`8` → хранить в формате `+7XXXXXXXXXX`. Невалидный телефон → ошибка формы.
2. **Обязательные поля:** серверная валидация дублирует клиентскую: service_id (существует и active), brand, model, имя, телефон, booking_date (не в прошлом, внутри демо-периода), booking_time (в списке демо-слотов).
3. **Защита `/admin`:** только Supabase Auth; RLS: `bookings`, `clients`, `vehicles`, `services` **не читаются и не пишутся анонимно**; публичный доступ — только через server actions (service role не светится в браузере) либо через узкие RPC с `security definer`. Аноним может создать заявку, но не может читать заявки/списки слотов сверх необходимого минимума.
4. **Секретные ключи:** `service_role key` и токен Telegram-бота — только в переменных окружения сервера (`.env`, не в `NEXT_PUBLIC_`); в браузер не попадают.
5. **RLS-политики (минимум):**
   - `services`: SELECT для anon (только is_active) — чтобы форма работала;
   - `clients/vehicles/bookings`: нет прямых прав anon/authenticated; все операции через server actions с service key на сервере;
   - либо вариант с RPC `create_booking(...)` (security definer) — открыт anon.
6. **Повторная отправка формы:** кнопка «Отправить» блокируется сразу после клика (isSubmitting) + серверный идемпотентный ключ (например, хэш телефона+даты+времени в течение короткого окна) — двойной клик не создаёт две заявки.
7. **Двойное бронирование:** гарантируется частичным уникальным индексом + атомарными RPC (см. 8.5), а не только проверкой в коде.
8. **Rate limiting (минимум):** на server action создания заявки — базовое ограничение (например, по IP через Upstash/простой in-memory счётчик) против спама формы.
9. **Причина отклонения** хранится в БД и никуда не отправляется клиенту (в демо канала уведомлений клиенту нет) — но поле обязательно для дисциплины.

# 11. Acceptance Criteria

**Клиентская часть:**
- [ ] AC-1. Клиент может пройти путь «услуга → авто → дата → время → контакты → подтверждение» за ≤ 3 минут и ≤ 5 нажатий «Далее».
- [ ] AC-2. Список услуг соответствует разделу 5.1; цены показаны только там, где указаны; выдуманных цен нет.
- [ ] AC-3. Прошедшие даты, даты вне демо-периода и время вне списка слотов выбрать невозможно.
- [ ] AC-4. Подтверждённый (занятый) слот отображается недоступным и не выбирается.
- [ ] AC-5. Форма не отправляется с пустым именем, телефоном, маркой, моделью или без выбранной услуги; ошибки понятны и показаны inline.
- [ ] AC-6. Невалидный телефон (не российский формат) отклоняется с понятной подсказкой.
- [ ] AC-7. После отправки — экран подтверждения с номером заявки; повторный клик/двойная отправка не создаёт дубликат.
- [ ] AC-8. Интерфейс корректно работает на экране 360 px без горизонтальной прокрутки.
- [ ] AC-9. В интерфейсе явно обозначено, что расписание демонстрационное (например, пометка «Демо-расписание» в подвале формы записи).

**Административная часть:**
- [ ] AC-10. Неавторизованный пользователь не видит `/admin` (редирект на вход).
- [ ] AC-11. Новая заявка клиента появляется в списке заявок со статусом «Новая».
- [ ] AC-12. Администратор может подтвердить заявку; после подтверждения слот становится занятым для клиентской формы.
- [ ] AC-13. Администратор может отклонить заявку только с указанием причины; слот освобождается.
- [ ] AC-14. Администратор может перенести заявку на свободный слот; старый слот освобождается, новый блокируется.
- [ ] AC-15. Подтвердить две заявки на одну дату/время невозможно: второй запрос отклоняется с сообщением «Время занято».
- [ ] AC-16. После обновления страницы админки данные (заявки, статусы, занятость) сохраняются.
- [ ] AC-17. Приложение работает полностью без настройки Telegram-уведомлений.
- [ ] AC-18. Счётчики dashboard соответствуют реальному количеству заявок по статусам.

# 14. Ограничения MVP

В демо **не реализуется**: CRM, личный кабинет, регистрация клиентов, онлайн-оплата, SMS, WhatsApp API, интеграция с 1С, склад, бухгалтерия, мобильное приложение, AI-чат, аналитика, мультифилиальность, реальные производственные расписания СТО.

Прочие осознанные упрощения демо:
- Демо-расписание единое для всех дней, без обеда и без разделения будни/выходные (DEMO DATA).
- Вместимость слота = 1 (`settings.capacity_per_slot`).
- Клиенту не отправляются уведомления о статусе заявки (нет согласованного канала) — только экран подтверждения.
- Списки услуг и демо-расписание наполняются seed-данными, интерфейс редактирования справочников не делается.
- Telegram-уведомление администратору — опциональный модуль; без него система полностью работоспособна.
