# 3. Текущий путь клиента

Реконструкция по сайту (то, что подтверждено, — без пометок; остальное — гипотезы):

1. **Попадание на сайт.** Клиент приходит из поиска («ремонт ходовой новосибирск»), карт (Яндекс/2ГИС), соцсетей, сарафана. **[ГИПОТЕЗА — точные источники трафика на сайте не измеряются]**
2. **Выбор услуги.** Клиент изучает меню (31 услуга), страницу услуги с SEO-текстом и прайс с ценами «от». Точную цену под свою модель он **не видит** — прайс прямо отправляет звонить.
3. **Обращение.** Все пути обращения — ручные и асинхронные: позвонить / написать в Telegram или WhatsApp / написать на e-mail / заказать обратный звонок (RedConnect).
4. **Запись.** **[ГИПОТЕЗА]** Администратор (или сам владелец) согласует дату и время вручную по телефону/переписке, записывает в бумажный журнал, Excel или заметки на телефоне. Подтверждения клиенту, напоминаний и отмены «в один клик» нет.
5. **Визит.** Клиент приезжает в согласованное время; в отзывах на Яндекс.Картах встречается «приехал по записи — сразу приняли» (внешний источник).

**Ключевое наблюдение:** между шагами «выбор услуги» и «запись» нет связующего цифрового механизма — клиента вынуждают позвонить. Это узкое место всей воронки.

# 4. Проблемы процесса записи

**Подтверждено сайтом:**
1. **Нет онлайн-записи вообще** — запись возможна только через ручной контакт (звонок/переписка).
2. **Цены «от …» + «уточняйте по телефону»** — клиент не может понять стоимость под свою машину без звонка; это снижает конверсию и создаёт лишнюю нагрузку на телефон.
3. **Один телефон на весь бизнес** — при занятости линии или вне часов приёма заявка теряется; в вечерний пик (до 21:00) администратор может быть занят на посте.
4. **Устаревший контент** (акции 2017 г.) подрывает доверие к онлайн-каналу в целом.

**Гипотезы [ГИПОТЕЗА]:**
5. Запись ведётся вручную → риск двойного бронирования одного поста, забытых записей, «человеческого фактора».
6. Нет напоминаний клиенту → неявки (no-show) без механизма подтверждения за день.
7. Нет ночного захвата заявок: сайт есть 24/7, а принимает заявки только телефон с 9:00.
8. Клиенту нечего показать: ни слота, ни «свободно/занято» — нет прозрачности расписания.
9. Повторным клиентам приходится каждый раз заново называть машину, телефон, VIN — нет карточки клиента.

**Потенциальные точки улучшения (по приоритету):**
- Кнопка «Записаться онлайн» + короткая форма записи (услуга → авто → дата/время → контакты) — закрывает главный разрыв.
- Виджет выбора свободного времени вместо переписки «когда вам удобно».
- Автоматическое уведомление администратору о новой заявке (Telegram-бот — канал уже используется).
- Напоминание клиенту о визите (SMS/Telegram) — **пока только как идея, в MVP минимум — подтверждение заявки**.

Что автоматизация даст конкретно этому бизнесу:

| Возможность | Эффект для «АвтоХирургии» |
|---|---|
| Онлайн-запись 24/7 | Заявки принимаются ночью и в часы, когда телефон занят; нет потерянных клиентов |
| Автоматическая проверка занятости | Исключение двойной записи на один пост без дисциплины «журнала» |
| Карточка клиента + автомобиль | Повторный клиент записывается за 30 секунд; механик заранее видит машину |
| Уведомления в Telegram администратору | Использует уже привычный канал; не нужна новая CRM-культура |

**Чего автоматизация НЕ должна делать на этом этапе:** оплата онлайн, CRM с воронками, склад, 1С, мобильное приложение, AI-диагностика (согласно ТЗ и здравому смыслу для малого СТО).

# 6. Концепция системы онлайн-записи

**Принципы:**
1. **Одна задача:** записать клиента на свободное время. Ничего лишнего.
2. **Два экрана:** форма для клиента + простая панель для администратора.
3. **Telegram как нервная система:** уведомления администратору и (опционально) подтверждения клиенту.
4. **Подтверждение человеком:** заявка не считается записью, пока администратор не подтвердил — СТО сохраняет контроль, клиенту не обещается недоступное.
5. **Масштабируемая основа:** сущности данных проектируются сразу как база (клиенты, авто, услуги, записи, слоты), а не как «таблица в Excel».

**Сценарий клиента:** выбрал услугу (1 клик из списка) → указал марку/модель/госномер → выбрал дату и свободное время из сетки → оставил имя и телефон → добавил комментарий (необязательно) → получил экран «Заявка принята, мы подтвердим по телефону/Telegram».

**Сценарий администратора:** пришло уведомление в Telegram → открыл панель → увидел заявку → подтвердил / перенёс / отменил → клиенту ушло подтверждение со временем.

# 7. MVP

### Обязательно в MVP (must have)
- **Клиентская форма записи:** услуга (выпадающий список из ~15–30 услуг сайта), марка/модель авто, госномер (опционально), дата, выбор свободного времени из сетки слотов, имя, телефон, комментарий.
- **Экран подтверждения заявки** клиенту («заявка принята, ожидайте подтверждения»).
- **Административная панель:** список заявок, просмотр заявки, смена статуса (новая / подтверждена / отменена / выполнена), перенос даты/времени.
- **Календарь/сетка занятости:** недельный вид, видно свободно/занято.
- **Блокировка слота:** невозможно подтвердить две записи на одно время (проверка на уровне данных).
- **Уведомление администратору в Telegram** о новой заявке.
- **Настройки:** график работы (ПН–ПТ 9:00–21:00, СБ–ВС 9:00–20:00), шаг слота (например, 1 час), количество одновременных постов.

### Можно добавить позже (should have, v1.1–v2)
- Напоминание клиенту о визите за день (Telegram/SMS).
- Услуги с разной длительностью (30/60/120 мин) и сеткой под длительность.
- Статус «ожидает запчасти», заметки к заявке, фото.
- Повторная запись «как в прошлый раз» по номеру телефона.
- Экспорт записей в Excel/календарь.
- Промокоды/акции, привязка к странице акций.
- Интеграция кнопки записи прямо на существующий сайт (виджет/ссылка).

### Сейчас не нужно (won't have)
- CRM, воронки продаж, сквозная аналитика.
- Онлайн-оплата и предоплата.
- Мобильное приложение (достаточно адаптивной веб-формы).
- Интеграция с 1С, складом, бухгалтерией.
- AI-диалоги, чат-боты.
- Мультифилиальность (у «АвтоХирургии» один адрес).
- Личный кабинет клиента с авторизацией.

# 9. UX-концепция

### Вариант A — «Максимально простой»
Один экран, одна колонка: 6 полей подряд (услуга → авто → дата → время → имя/телефон → комментарий) → кнопка «Записаться». Без картинок, без каруселей. Самый быстрый путь, минимум разработки.
*Минус:* выглядит «самодельным», слабо усиливает доверие.

### Вариант B — «Современный»
Пошаговый мастер (wizard) с прогрессом, карточки услуг с ценами «от», анимированная сетка слотов, авто-подстановка данных при повторном визите. Тёмно-синяя/графитовая палитра, крупные кнопки, мобильный first.
*Минус:* больше разработки и тестирования; визуально «не из этой вселенной» рядом с текущим сайтом.

### Вариант C — «Как существующий сайт AutoSurgery»
Форма в фирменной красно-бело-чёрной гамме, с той же типографикой и шапкой, встроена как страница `/zapis.html` рядом с текущими страницами. Клиент не замечает перехода между сайтом и записью.
*Минус:* наследует устаревший визуальный язык сайта; тянет дизайн-систему 2017 года в новый продукт.

### Выбранный вариант: **A+ (простой каркас с элементами C)**
**Рекомендация: Вариант A по структуре + палитра и шапка из Варианта C.**

Почему:
1. **Ценность MVP — скорость и ясность, а не «вау-дизайн».** Клиент должен записаться за 1–2 минуты на любом телефоне — это критерий успеха №1.
2. **Демонстрация владельцу:** единый экран понятен без объяснений, владелец сразу видит весь процесс.
3. **Разработка одним разработчиком:** один экран формы + одна панель администратора — реалистичный объём.
4. **Стилистическая преемственность (шапка, цвета, логотип)** снимает вопрос «а это вообще наш сайт?» у владельца и у клиентов.
5. Вариант B остаётся дорожной картой: когда MVP приживётся, клиентскую часть можно перерисовать независимо от логики записи.

**Структура клиентской части (финальная):**
1. Шаг 1 — Услуга (список из каталога, с ценой «от» где есть).
2. Шаг 2 — Автомобиль: марка, модель, год (опционально), госномер (опционально).
3. Шаг 3 — Дата и время: календарь (без прошедших дат и выходных вне графика) + сетка слотов «свободно/занято».
4. Шаг 4 — Контакты: имя, телефон (+ опционально Telegram-ник).
5. Шаг 5 — Комментарий (необязательно) → кнопка «Отправить заявку».
6. Экран подтверждения: «Заявка №… принята. Мы подтвердим время по телефону в течение рабочего дня».

**Структура административной части (финальная):**
1. **Список заявок** с фильтром по статусу и дате.
2. **Календарь** (неделя): посты × слоты, цветовые статусы.
3. **Карточка заявки:** клиент, телефон, авто, услуга, комментарий, время создания.
4. **Действия:** подтвердить, отменить (с причиной), перенести (выбрать новый слот), отметить выполненной.
5. **Уведомления:** Telegram-бот «новая заявка» + напоминание о неподтверждённых заявках.

```
- updated_at

time_slots / schedule
- id
- date
- time_start
- time_end
- capacity         (сколько машин можно принять параллельно)
- booked_count     (сколько подтверждено; держится транзакционно)
- is_blocked       (ручная блокировка, праздники)

booking_slot       (связь записи со слотом, если переносы/несколько слотов)
- booking_id       → bookings.id
- slot_id          → time_slots.id

settings (одна запись)
- work_schedule    (ПН–ПТ 09:00–21:00, СБ–ВС 09:00–20:00)
- slot_step_min    (например, 60)
- notify_telegram_chat_id (куда слать уведомления)
```

**Ключевые правила целостности:**
- Одна запись = один слот; подтверждение записи увеличивает `booked_count` атомарно → двойное бронирование невозможно.
- Слоты генерируются по расписанию из `settings`, а не хранятся «на год вперёд».

# 11. Критерии успешности MVP

**Функциональные (должны выполняться всегда):**
1. Клиент проходит путь от открытия формы до отправки заявки **не более чем за 3 минуты** и **не более чем за 5 действий** (услуга → авто → дата/время → контакты → отправка).
2. Клиент **физически не может выбрать** прошедшую дату, время вне графика или уже занятый слот.
3. **Невозможно подтвердить две записи на одно занятое время** (проверяется на уровне данных, а не «аккуратностью администратора»).
4. Администратор **видит новую заявку в течение 1 минуты** после отправки (Telegram-уведомление).
5. Администратор может подтвердить, отменить или перенести заявку **не более чем за 3 клика**.
6. После действий администратора статус заявки корректно отображается и не теряется при перезагрузке.

**Бизнес-пилот (проверяются за 2–4 недели тестовой эксплуатации):**
7. Минимум 30% новых заявок приходит через онлайн-форму (а не только по телефону). **[ГИПОТЕЗА-цель]**
8. Ни одного случая двойной записи на один пост за период пилота.
9. Владелец подтверждает, что панель проще журнала/переписки (субъективный критерий — интервью после пилота).
10. Время подтверждения заявки администратором — в пределах рабочего дня.

# 12. Что неизвестно и требует уточнения у владельца

1. **Сколько постов/боксов** принимает машины одновременно? (От этого зависит `capacity` слотов.) — **информация на сайте не обнаружена.**
2. **Как ведётся запись сейчас** — бумажный журнал, Excel, телефон? Есть ли администратор или записью занимается механик/владелец?
3. **Реальная длительность типовых работ** (замена масла 30 мин? ремонт ходовой — полдня?) — для корректной сетки слотов.
4. **Сколько времени в день уходит на телефонные согласования** записи (база для оценки эффекта автоматизации)?
5. **Кто и как подтверждает заявки** — нужен ли доступ к панели с телефона, сколько человек будут ей пользоваться?
6. **Юридический статус и согласие на обработку ПДн**: на сайте есть «Политика обработки персональных данных» — актуальна ли она для новой формы, нужно ли чекбокс-согласие?
7. **Хотят ли владельцы подтверждать каждую заявку вручную** или разрешить автозапись «как в кинотеатре»?
8. **Цели на будущее**: планируется ли второй адрес/филиал, найм администратора, рост числа постов (влияет на архитектуру)?
9. **Каналы уведомлений клиенту**: разрешены ли SMS-рассылки, есть ли бюджет на SMS-шлюз или только Telegram/WhatsApp-ссылки?
10. **Брендинг**: есть ли логотип в векторе/высоком разрешении, фирменные цвета (на сайте красно-бело-чёрная гамма — подтвердить)?
11. **Домен и хостинг**: кто управляет autosurgery.ru, можно ли разместить форму на поддомене/подпапке или нужен отдельный хостинг?
12. **Актуальность цен**: прайс «от … руб.» соответствует ли реальным ценам 2026 года? (Sitemap указывает на 2017 год.)
