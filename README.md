# AutoSurgery Booking — демонстрационный MVP онлайн-записи

СТО «АвтоХирургия», Новосибирск. Демо-версия онлайн-записи: клиентская форма,
админ-панель заявок, защита от двойного бронирования на уровне БД.

ТЗ: `docs/requirements.md` · Исследование: `docs/research.md`

## Стек

Next.js 16 (App Router) · TypeScript · Tailwind CSS v4 · shadcn/ui · Supabase (PostgreSQL + Auth + RLS) · Zod

## Команды

```bash
npm install        # установка зависимостей
npm run dev        # dev-сервер (http://localhost:3000)
npm run lint       # ESLint
npm run build      # production build (webpack-режим, см. ниже)
npm start          # запуск production-сервера
```

## Пошаговая инструкция по запуску

### 1. Создание Supabase-проекта

1. Зайдите на [supabase.com](https://supabase.com) и создайте бесплатный проект
   (New project → имя, пароль БД, регион — ближайший к России доступный).
2. Дождитесь окончания инициализации проекта (~1 минута).
3. Возьмите ключи: **Project Settings → API**:
   - **Project URL** — нужен для `NEXT_PUBLIC_SUPABASE_URL`;
   - **anon public** key — нужен для `NEXT_PUBLIC_SUPABASE_ANON_KEY`.

Service role key **не используется**: вся запись идёт через RPC-функции
(security definer), а админские действия — через Supabase Auth (см. раздел
«Почему не нужен service_role key» ниже). Секреты в браузер не попадают.

### 2. SQL-миграции

1. В панели Supabase откройте **SQL Editor** (иконка базы в левом меню).
2. Создайте новый запрос, скопируйте целиком содержимое файла
   `supabase/migrations/0001_init.sql` и нажмите **Run**.

   Миграция создаёт: таблицы `services`, `clients`, `vehicles`, `bookings`,
   `settings`; частичный уникальный индекс против двойного бронирования;
   триггер `updated_at`; RLS-политики; 8 RPC-функций (`create_booking`,
   `get_booked_slots`, `get_booking_public`, `confirm_booking`,
   `cancel_booking`, `reschedule_booking`, `complete_booking`, плюс helper).

   Порядок выполнения: `0001_init.sql` — **первым и обязательно до seed**.

### 3. Seed (демо-данные)

В том же **SQL Editor** новым запросом выполните `supabase/seed.sql` → **Run**.

Загружается:
- ~51 услуга из ТЗ (цены только там, где они указаны в ТЗ; у остальных
  `price_from = NULL` → в форме «цена по телефону»);
- демо-расписание (`settings.demo_schedule`): 14 дней вперёд, слоты
  09:00, 10:00, 11:00, 12:00, 14:00, 15:00, 16:00, 17:00, 18:00, вместимость 1;
- 7 тестовых заявок во всех статусах; две подтверждённые занимают слоты
  `current_date + 1` 11:00 и `current_date + 2` 14:00.

Все демо-данные помечены **DEMO DATA** в комментариях SQL и отмечены
плашкой «Демо-расписание» в интерфейсе.

### 4. Администратор

1. **Authentication → Users → Add user → Create new user**.
2. Введите e-mail и пароль администратора (например, `admin@demo.local` и
   любой пароль не короче 6 символов).
3. Включите **Auto Confirm User** (или подтвердите e-mail вручную).

Публичной регистрации нет — вход в `/admin` только по этому пользователю.

### 5. `.env.local`

Скопируйте `.env.example` в `.env.local` (в корне проекта) и подставьте
значения из **Settings → API**:

```env
NEXT_PUBLIC_SUPABASE_URL=https://ваш-проект.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...   # anon public key
# TELEGRAM_BOT_TOKEN=...   # опционально, на будущее; в демо не используется
```

Перезапустите dev-сервер после изменения `.env.local` (`Ctrl+C`, затем
`npm run dev` заново) — переменные читаются при старте.

### 6. Запуск

```bash
npm install
npm run dev
```

- Клиентская запись: http://localhost:3000/booking
- Админ-панель: http://localhost:3000/admin (логин/пароль из шага 4)

Если `.env.local` заполнен, но что-то не работает — проверьте, что миграция
из шага 2 выполнена и сервер перезапущен.

## Почему не нужен service_role key

Вся запись идёт через RPC `create_booking` (security definer) + RLS, админские
действия — через RPC `confirm_booking` / `cancel_booking` / `reschedule_booking` /
`complete_booking` под сессией Supabase Auth. Приложению достаточно anon key;
секреты в браузер не попадают.

## Архитектура данных

- Уникальный частичный индекс `bookings_one_confirmed_per_slot` запрещает две
  подтверждённые заявки на одну дату/время — двойное бронирование невозможно
  на уровне БД, а не только в коде.
- Допустимые переходы статусов (`new → confirmed/cancelled`,
  `confirmed → completed/cancelled/перенос`) реализованы внутри RPC.
- Слот при статусе `new` не блокируется (согласно ТЗ); занят становится после
  подтверждения администратором.

## Демо-расписание

⚠️ DEMO DATA, не реальное расписание СТО: 14 дней вперёд, слоты
09:00–12:00 и 14:00–18:00, вместимость 1. Пометка «Демо-расписание» видна

## Demo checklist

Проверка перед показом владельцу (порядок — как ниже):

- [ ] `0001_init.sql` выполнен в SQL Editor миграциями (без ошибок)
- [ ] `seed.sql` выполнен; в таблице `services` ~51 строка
- [ ] Пользователь администратора создан в Authentication (auto-confirm)
- [ ] `.env.local` заполнен, dev-сервер перезапущен
- [ ] `/booking` → пройти весь flow до экрана «Заявка принята»
- [ ] Заявка видна в `/admin` со статусом «Новая»
- [ ] Подтверждение заявки → слот становится зачёркнутым в клиентской форме
- [ ] Повторное подтверждение другой заявки на тот же слот → ошибка «Время занято»
- [ ] Отклонение без причины невозможно (модалка требует причину)
- [ ] Перенос подтверждённой заявки: старый слот освобождается, новый блокируется
- [ ] `/admin` без логина перенаправляет на `/admin/login`
- [ ] Экран 360×640 без горизонтального скролла (кроме ленты дат — она листается намеренно)
- [ ] Плашки «ДЕМО-РАСПИСАНИЕ» на месте (форма даты/времени, подтверждение)

## Особенность окружения (важно)

Проект расположен по пути с кириллицей (`C:\Users\Роман\...`). Turbopack
(`next build` / `next dev` по умолчанию) в таком расположении не может
запустить вспомогательный node-процесс для обработки CSS («program not
found»). Поэтому скрипты используют поддерживаемый Next 16 webpack-режим:
`next build --webpack` и `next dev --webpack`. На путях без кириллицы можно
вернуть обычные команды `next build` / `next dev`.
